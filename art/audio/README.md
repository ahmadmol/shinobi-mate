# ShinobiMate audio packs — Phase 1

Playback is owned by `AudioManager`; callers enqueue event IDs and never decode or open audio.
Naruto and Sasuke have pack-owned `conf/sounds.json` files; `audio/common` provides generic events
and legacy aliases for packs without audio. There are no Naruto/Sasuke branches in playback code.

```json
{
  "version": 1,
  "events": {
    "movement.footstep": {
      "category": "MOVEMENT",
      "variations": ["sounds/movement/footstep_01.wav", "sounds/movement/footstep_02.wav"],
      "volume": 0.4,
      "cooldown": 240,
      "maxConcurrent": 2,
      "loop": false,
      "priority": 10,
      "maxDurationMs": 3000
    }
  }
}
```

Categories: `MOVEMENT`, `COMBAT`, `WEAPON`, `VFX`, `CHARACTER`, `UI`. Volume is linear 0–1;
cooldown and safety duration are milliseconds. Priority is 0–100, higher wins. Empty/unknown sound
IDs and missing or malformed assets remain optional; warnings are deduplicated and gameplay continues.
Paths must remain within the pack. Manifests are capped at 64 KiB and 128 events; each event has up to 16 variations.

Ordinary action XML pose markers use `SoundEvent="movement.footstep"`, once at pose entry.
Combat animation frames can use `soundEvent="movement.run"`. Attack XML uses `startupSound`,
`attackSound`, `impactSound`, optional `readySound`, `loopSound`, `afterSound`. Combo strikes can
override `attackSound` and `impactSound`. Impact events are emitted only by confirmed collision;
blocks and parries use their own cues. Signature/weapon impacts resolve from the attacker's pack,
with pan calculated at the victim. Startup/loop handles are stopped at active phase, interruption,
parry, suspension, KO, removal, reload and match end. Loops also expire if lifecycle cancellation is lost.

API examples:

```java
AudioManager.play("ui.click");
var scope = new AudioManager.Scope();
var handle = AudioManager.global().playCharacter(packId, "movement.jump", scope, pan);
AudioManager.global().stop(handle);
AudioManager.global().stop(scope); // Terminal: create a fresh scope for the next battle/mascot.
```

Two fixed daemon workers: one for manifests/PCM cache/arbitration, one for output mixing. The
play queue admits at most 64 requests, with eight slots reserved from movement floods; stale
requests older than 180 ms are dropped. Cleanup and volume refresh commands are coalesced.
At most 12 software voices share one stereo 22050 Hz PCM16 SourceDataLine. No Clip is allocated.
The device is silently warmed once during pack preload, off EDT. The output line closes after 400 ms of silence and on exit. Software gain and pan work without
requiring hardware MASTER_GAIN or PAN controls. The 4096-byte device buffer is about 46 ms.

Category limits: movement 3, UI 2, character 2, combat/weapon/VFX 8 each, with global limit 12.
Per-event concurrency and global pack/event cooldowns apply across duplicate mascots. Random
variation selection excludes the previous file. Decoded PCM uses an LRU bounded at 128 files
and 8 MiB; input WAVs are limited to 2 MiB and decoded files to 1 MiB. Failed files back off 30 s.
Only metadata for 32 recently used packs is retained. Character removal retires its audio scope;
pack reload invalidates PCM and metadata. App shutdown cancels workers and closes native output.

All 155 WAVs are original procedural SFX, generated by `tools/build-audio-phase1.py` using only
the Python standard library. No external recordings, voices, anime episode audio, OST or licensed
third-party sample libraries are used. Per-file SHA-256/source records are in `asset-provenance.json`.
`grunt` currently uses a generic generated breath, not an actor voice; bespoke voiced reactions remain optional.

Reproduce assets with Python 3: `python tools/build-audio-phase1.py`.
Run checks: `tools/check-audio-phase1.ps1 -Jdk <JDK-21-or-newer> -Native`.
Add `-Visual -SkipBuild` to open the isolated native visual/audio QA panel. Close that panel before
running Maven clean on Windows, because its JVM holds the JAR open. Test profiles live under
`output/audio-phase1`, preserving the user's normal `%LOCALAPPDATA%/ShinobiMate` preferences.

The final measured report and remaining subjective listening acceptance are recorded in `PHASE1_REPORT.md`.
